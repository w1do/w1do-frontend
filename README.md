## 📨 Приём заявок

Формы сайта отправляют заявку на собственный роут `POST /api/lead`, который проксирует её
в платформу (`POST /api/v1/leads` на `backend.w1do.ru`), добавляя заголовок `X-Api-Key`
на стороне сервера. Ключ не попадает в клиентскую сборку.

Перед отправкой формы пользователь должен отметить `legalConsent`. Клиентская форма и
серверный роут проверяют согласие; `/api/lead` добавляет в payload время принятия и
адреса юридических документов из `src/lib/legal.ts`.

Юридические документы открываются по `/docs/<slug>`. Роут `src/pages/docs/[slug].astro`
берёт опубликованную страницу W1DO через `GET /api/v1/content/pages/{slug}`, поэтому
для работы документов нужен тот же серверный `LEADS_API_KEY`.

Переменные окружения:

| Переменная | Область | Назначение |
| :--- | :--- | :--- |
| `LEADS_API_KEY` | сервер, секрет | Ключ проекта для заголовка `X-Api-Key`. Читается в рантайме |
| `LEADS_API_BASE_URL` | сервер, секрет | Базовый адрес платформы. По умолчанию `https://backend.w1do.ru` |
| `PUBLIC_LEADS_ENDPOINT` | клиент | Собственный роут приёма. По умолчанию `/api/lead` |

**Важно для развёртывания:** роут `/api/lead` рендерится по запросу (`prerender = false`),
поэтому сайт обязан выполняться как node-сервер:

```bash
LEADS_API_KEY=pk_live_… node ./dist/server/entry.mjs
```

Выкладка одной статики из `dist/client` приём заявок сломает. `LEADS_API_KEY` задаётся
в окружении рантайма (в контейнере — переменной окружения), а не на этапе сборки:
без него роут отвечает ошибкой и пишет об этом в лог сервера.

## Кейсы W1DO

Коллекция `cases` в W1DO — источник карточек и страниц кейсов. Архив и страницы кейсов
читают опубликованные записи через серверный API с `X-Api-Key`; используется секрет
`LEADS_API_KEY` и базовый URL `LEADS_API_BASE_URL`, описанные выше. Ключ нужен
в окружении запуска серверного контейнера. Локальные Markdown-кейсы не используются.

## Услуги W1DO

Коллекция `services` содержит все разделы и вложенные страницы услуг, SEO-метаданные,
текст, FAQ и блоки шаблона. Серверный адаптер читает опубликованные записи через W1DO API;
поля `cluster_slug`, `post_slug` и `public_path` сохраняют существующие адреса сайта.
Основной источник страниц услуг — CMS, локальные Markdown-файлы больше не участвуют в выводе.
Страницы читают CMS на сервере при запросе; список услуг кешируется на 60 секунд.
Изменения текста и SEO в W1DO появляются без новой сборки.

## Блог в W1DO CMS

Статьи хранятся в штатных постах CMS: категории, именованные Markdown-блоки, теги, обложки и SEO.
`src/lib/server/w1do/blog.ts` получает опубликованные посты через серверный API.
Маршруты `/blog`, `/blog/page/N`, `/blog/slug` и `/blog-sitemap.xml` обновляются при запросе.
Исходная дата статьи хранится в `seo.json_ld.datePublished`.
Блок последних статей на главной обновляется при запросе.

## Мультирегиональность

Главная города по умолчанию (Москва) доступна на `/`, остальных — на `/irkutsk`, `/saint_petersburg` и других `/{city}`.
Услуги, блог, контакты и остальные страницы имеют общие адреса без префикса города.
Slug, список включённых городов и SEO берутся из
`GET /api/v1/content/cities` через серверный адаптер с `X-Api-Key`; кеш — 60 секунд.
Переключатель на главной ведёт на главную выбранного города. Адрес `/moscow` перенаправляется
с 301 на `/`. Старые адреса `/city/services` и подобные
перенаправляются на общие страницы; query-параметры сохраняются.

`W1DO_DEFAULT_CITY=moscow` соответствует проверенной настройке CMS. Публичный API
пока не отдаёт `default_city`: при изменении этого значения в CMS обновите переменную
окружения серверного контейнера. Ключи остаются только на сервере.

На главной города используются CMS title, description, keywords, robots, Open Graph
и JSON-LD. На остальных страницах используется собственное SEO без городского контекста.
Ссылки с городской главной ведут на общие страницы; ссылка «Главная» сохраняет город. CMS canonical вида
`/cities/moscow` заменяется действующим адресом `/`.

Общий `/sitemap-index.xml` включает две карты без пересечений:

- `/cms-sitemap.xml` — `GET /api/v1/sitemap.xml` из W1DO с серверным ключом;
  если новая ручка отвечает 404, используется совместимый `GET /sitemap.xml`.
  Адреса CMS нормализуются под маршруты фронтенда, сохраняется `lastmod`.
- `/sitemap-0.xml` — собственные страницы Astro, лендинги и пагинация блога.

Материалы CMS и собственные внутренние страницы включаются по одному разу без
городского префикса. Дополнительно включаются главные включённых городов; города
с `noindex` не включаются. Старые blog/case/content sitemap endpoints сохранены для совместимости.
`robots.txt` ссылается только на общий индекс. `/llms.txt` и `/llms-full.txt` формируются
на сервере с актуальными региональными ссылками вместо генерации при сборке.

Сайт остаётся на Astro без SPA, страницы рендерятся сервером Node. Для деплоя
нужно запускать `dist/server/entry.mjs`, как в существующем Dockerfile.
Проверка логики: `node --experimental-strip-types --test tests/regions.test.ts`.
