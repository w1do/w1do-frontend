# CLAUDE.md

## Как работать в этом проекте

1. Сначала изучи текущий проект через память: `memory_search`, `memory_get_context`,
   `memory_project_structure`, и только потом `memory_get_file` по нужным строкам.
   Проект строится только из того, что описывает память. Не сканируй `src` и не читай файлы напрямую.
2. Перед кодом или спорным решением вызови MCP `preferences`.
3. Если задача про CMS, сначала изучи MCP `w1do`, затем текущие страницы,
   коллекции и категории.
4. Если нужны изображения, иконки или SVG-декор, используй MCP `assets`, держи
   один визуальный стиль и складывай файлы локально.
5. Делай изменение узко: только то, что нужно для задачи.
6. Память проекта — главный приоритет (см. раздел ниже). Работай с файлами только через
   MCP `project-memory`. Никаких CLI `memory`, `memory watch` и прямой записи в `.memory/`.

## Память проекта — главный приоритет

- Память `project-memory` — единственный источник знаний о проекте. Любой файл, компонент, страница,
  layout, API-маршрут, стиль и контентная запись существует для разработки только если описаны в памяти.
- Никогда не выдумывай компоненты, props, маршруты, API и хелперы. Если нужного нет в памяти,
  напиши `не найдено в памяти проекта` и спроси пользователя. Новый файл создаётся только после явного «да».
- Перед использованием или правкой любого компонента найди его через `memory_search`/`memory_get_context`,
  затем `memory_get_file` по нужным строкам.
- Синхронизация с памятью в той же задаче, что и изменение файла:
  - добавил или изменил файл — `memory_update` по пути или `memory_sync` для пачки;
  - удалил или переименовал файл — `memory_sync` удалит запись; проверь `memory_search`, что старого пути нет;
  - каждая новая фича, страница или компонент получает аннотацию `memory_annotate` (до 200 символов).
    В `content_hash` передавай `indexed_hash` из `memory_get_file`. Хеши из результатов поиска — это хеши чанков, аннотация с ними не сохранится.
- Перед отчётом о выполнении вызови `memory_status`: `stale_files` и `unindexed_files` должны быть 0, `errors` — 0.
  Задача не считается выполненной, пока они не нулевые.
- Если MCP `project-memory` недоступен, остановись и напиши `Project memory: unavailable`.
  Не переходи к сканированию репозитория.

## React / Astro / Vue

- Для Astro предпочитай `.astro`-страницы и компоненты для статической структуры,
  SEO, layouts и контента.
- React/Vue используй только там, где нужен интерактив или локальное состояние.
- Не делай клиентский SPA там, где достаточно Astro и небольшого острова.
- Серверные данные получай через адаптеры и серверный слой, а не прямым `fetch`
  из UI-компонентов.
- Компоненты называй по смыслу, держи их читабельными, без "умных" цепочек и
  лишних абстракций.

## Визуальная работа

- Если есть референс, сначала опиши видимые блоки и замерь: ширины, высоты,
  отступы, радиусы, цвета, шрифты, состояния и адаптив.
- Верстай 1:1. Расхождения по цвету, размеру, радиусу, отступам и композиции
  считаются дефектом.
- Не используй готовые UI-киты, если они меняют стиль референса.
- Иконки, иллюстрации и фоновые SVG бери из MCP `assets`, а не рисуй от руки.
- CSS организуй через понятные токены: цвета, радиусы, размеры, z-index,
  контейнеры и состояния.

## Проверка

- Для обычной правки запускай `npm run build`.
- Для визуальной правки запускай dev-сервер и проверяй страницу в браузере.
- Для референса делай скриншот в той же ширине и сравнивай с эталоном.
- Перед финальным ответом проверь, что нет лишних изменений, секретов в коде и
  прямых запросов к платформе из UI.

## Ответ пользователю

- Пиши кратко и понятно: что сделал, где файлы, чем проверил.
- Не перекладывай на пользователя то, что можно проверить локально.
- Если что-то не удалось проверить, скажи прямо.
