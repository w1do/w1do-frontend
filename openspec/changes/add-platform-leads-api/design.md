## Context

См. `proposal.md` — Why. Ограничения, формирующие подход:

- Astro 6 с `output: 'static'` и `@astrojs/node` в режиме `standalone`. Серверные роуты в такой конфигурации возможны только при явном `export const prerender = false` в файле роута; остальной сайт остаётся статикой.
- Продакшен-контейнер (`Dockerfile`) запускает `node ./dist/server/entry.mjs`, то есть node-сервер в рантайме уже есть — прокси-роут будет обслуживаться.
- Обе формы (`ContactForm.tsx`, `CtaForm.tsx`) — React-острова с `client:load`, разделяющие единственный хук `src/hooks/useContactForm.ts`. Разметка и классы взяты из готового шаблона (`contact-form`, `help-block with-errors`, `btn-default`), их структуру ломать не нужно.
- Контракт платформы описан в `LLM.txt`: `POST /api/v1/leads`, заголовок `X-Api-Key`, конверты `{"data": …}` / `{"error": {...}}`, honeypot-поле `max`.
- Поля форм: `fname`, `lname`, `phone`, `email`, `message`. Платформа принимает плоские `email`, `phone`, `subject`, `message`, `source`, `payload` — имя и фамилия не имеют прямого соответствия и должны быть уложены в `subject`/`message`.

## Goals / Non-Goals

**Goals:**

- Единственный путь заявки: браузер → собственный роут сайта → платформа.
- Ключ `pk_live_…` живёт только в серверном окружении; клиентская сборка о нём не знает.
- Единая точка формирования полезной нагрузки — хук, чтобы обе формы вели себя одинаково.
- Понятные сообщения об ошибке для посетителя и достаточная диагностика (`trace_id`) в логе сервера.

**Non-Goals:**

- Персистентное хранение заявок на стороне сайта, очередь ретраев, офлайн-буфер.
- Капча и rate-limit по IP: в этом изменении защита от ботов ограничена honeypot-полем.
- Прочие разделы `LLM.txt` — контент, аналитика, оплаты, пользователи сайта.
- Вывод n8n-сценария из эксплуатации на стороне n8n (сайт просто перестаёт туда обращаться).

## Decisions

### Решение 1: Серверный прокси-роут вместо прямого запроса из браузера

Добавляем `src/pages/api/lead.ts` с `export const prerender = false` и обработчиком `POST`. Роут читает JSON тела, валидирует, добавляет `X-Api-Key` из `import.meta.env.LEADS_API_KEY` и вызывает платформу.

Почему так: ключ проекта один на весь проект и, будучи выложен в бандл, позволяет любому создавать заявки от имени сайта; ротация ключа требует перевыпуска (платформа показывает его один раз). Прокси даёт также серверную валидацию, отсев honeypot до внешнего вызова и место для будущего rate-limit.

Альтернативы:
- *Прямой `fetch` из браузера с `PUBLIC_LEADS_API_KEY`* — работает на чистой статике, но публикует ключ. Отклонено по решению пользователя.
- *Прокси с фолбэком на прямой запрос* — сохраняет ключ в бандле, то есть не даёт выигрыша в безопасности. Отклонено.

Следствие: сайт обязан выкладываться как node-сервер. Если когда-нибудь понадобится выкладка чистой статики, форму придётся переводить на прямой запрос — это фиксируется в разделе рисков.

### Решение 2: Адрес эндпоинта — публичная переменная, ключ — приватная

Три ключа окружения:

| Ключ | Область | Назначение |
| --- | --- | --- |
| `LEADS_API_BASE_URL` | сервер | Базовый адрес платформы, `https://backend.w1do.ru` |
| `LEADS_API_KEY` | сервер | Значение заголовка `X-Api-Key` |
| `PUBLIC_LEADS_ENDPOINT` | клиент | Собственный роут сайта, `/api/lead` |

`PUBLIC_LEADS_ENDPOINT` публичный намеренно: это относительный путь того же домена, секрета не содержит, но позволяет перенастроить адрес приёма без правки кода. Идентификатор проекта из `LLM.txt` в переменные не выносим: платформа определяет проект по самому ключу.

Читать серверные значения через `import.meta.env` нельзя: Vite подставляет их на этапе сборки, из-за чего ключ впечатывается в `dist/server`, а проверка `if (!apiKey)` вырезается как мёртвый код (проверено на реальной сборке). Поэтому `LEADS_API_KEY` и `LEADS_API_BASE_URL` объявлены в `astro.config.mjs` через `envField.string({ context: 'server', access: 'secret', optional: true })` и читаются роутом из `astro:env/server`. Так значения берутся из окружения в рантайме, в сборку не попадают, а сценарий «ключ не задан» остаётся достижимым.

Отсутствующий `LEADS_API_KEY` роут трактует как ошибку конфигурации: отвечает `500` с нейтральным текстом для посетителя и пишет явное сообщение в лог сервера. Для `LEADS_API_BASE_URL` в коде остаётся значение по умолчанию `https://backend.w1do.ru` — адрес не секрет.

### Решение 3: Отображение полей формы на контракт платформы

| Поле платформы | Источник |
| --- | --- |
| `email` | поле `email`; при пустом значении ключ опускается, а не отправляется строкой «не указан» |
| `phone` | поле `phone`, обязательное |
| `subject` | `Заявка с сайта: <Имя Фамилия>` |
| `message` | поле `message`; при пустом — `Имя: <Имя Фамилия>` |
| `source` | `contact-page` для `ContactForm`, `cta-block` для `CtaForm` |
| `payload` | UTM-метки из `location.search`, `page` — путь страницы, `referrer` — при наличии |
| `max` | honeypot; при непустом значении заявка отбрасывается |

`source` передаётся в хук новым пропсом формы, а не выводится из адреса страницы: блок CTA встречается на многих страницах, и по пути их не различить. Прежний проп `project` удаляется — он существовал только для n8n, платформа определяет проект по ключу.

Отправка пустого email как строки «не указан» (текущее поведение) заменена на опускание ключа: платформа валидирует формат email, и мусорное значение получит отказ.

### Решение 4: Разбор конвертов платформы

Хук и роут читают ответ единообразно: при `response.ok` берут `data`, иначе — `error.message` для показа посетителю и `error.trace_id` для лога сервера. Роут не пробрасывает тело ответа платформы наружу дословно: наружу уходит `{ ok: true, id }` либо `{ ok: false, message }` с текстом, пригодным для показа, — `details` и `trace_id` остаются в логе сервера, чтобы внутренние подробности платформы не утекали в браузер.

Таймаут исходящего запроса к платформе — 10 секунд через `AbortSignal.timeout`, чтобы форма не висела бесконечно при недоступной платформе.

### Решение 5: Honeypot-поле в разметке

Поле `max` добавляется в обе формы как `<input type="text" name="max" tabIndex={-1} autoComplete="off" aria-hidden="true">` в контейнере, скрытом стилем вне потока (`position: absolute; left: -9999px`), а не `display: none` и не `type="hidden"`: часть ботов пропускает скрытые дисплеем и заполняет только видимые в DOM поля. Скрытие выполняется inline-стилем, чтобы не зависеть от подключённых CSS-файлов шаблона.

Заполненная ловушка обрабатывается на сервере и даёт «тихий успех» — тот же ответ, что и принятая заявка, чтобы бот не смог определить факт отсева. Клиент дополнительно проверяет ловушку до отправки, чтобы не тратить сетевой запрос.

### Решение 6: Снос легаси-обработчика форм шаблона

`public/js/function.js` навешивал на `#contactForm` jQuery-валидатор шаблона и слал форму на несуществующий `form-process.php`, а `submitMSG` переписывал `#msgSubmit`. Обработчик перехватывал submit раньше React: пока пусто любое поле с `required` (включая email), React-обработчик не вызывался вовсе, и заявку нельзя было отправить без email.

Блок «Contact form validation» удалён из `function.js`, подключение `validator.min.js` убрано из `Layout.astro`, формы переведены на чистый React: убраны пустые контейнеры `help-block` под валидатор шаблона и дублирующиеся `id="msgSubmit"`, идентификаторы форм разведены (`leadForm` и `ctaLeadForm`), `required` оставлен только на имени и телефоне — как того требует спецификация.

Альтернатива — только переименовать идентификаторы форм, оставив мёртвый обработчик в `function.js` — отклонена: код всё равно шлёт запросы на несуществующий адрес и путает следующего читателя.

## Risks / Trade-offs

- **Роут требует node-рантайма; выкладка чистой статики ломает приём заявок** → в `README.md` фиксируется требование запуска `dist/server/entry.mjs` и наличия `LEADS_API_KEY`; проверка выполняется дымовым тестом после развёртывания.
- **Забытый `LEADS_API_KEY` в окружении продакшена молча ломает все формы** → роут отвечает явной ошибкой конфигурации и логирует её отдельным сообщением; в задачи включена проверка на стенде до выкладки.
- **Отключение n8n обрывает текущий канал уведомлений о заявках** → в задачах предусмотрена контрольная отправка через новую цепочку и подтверждение, что заявка видна в платформе, до вывода старого канала из эксплуатации.
- **Honeypot без rate-limit не остановит целевой спам** → принятая на этом этапе цена; серверный роут оставляет место для добавления ограничения по IP без правок клиента.
- **Ключ `pk_live_…` из `LLM.txt` присутствует в рабочем дереве** → `LLM.txt` не должен попасть в публичную выдачу сайта, а `.env.example` содержит только плейсхолдеры; сам `.env` уже в `.gitignore`.
- **Свободный `payload` может принять больше данных, чем нужно** → передаются только явно перечисленные ключи (UTM, `page`, `referrer`), произвольные поля формы в `payload` не попадают.

## Migration Plan

1. Добавить ключи в `.env.example` (плейсхолдеры) и `.env` (реальные значения из `LLM.txt`).
2. Добавить роут `src/pages/api/lead.ts`, не трогая формы, — старый путь через n8n продолжает работать.
3. Перевести хук и обе формы на новый роут, удалить пропсы `endpoint`/`project`.
4. Проверить на стенде: успешная заявка, ошибка валидации, заполненная ловушка, недоступность платформы; убедиться, что заявка видна в платформе.
5. Убедиться поиском по `dist/`, что ключа нет в клиентской сборке.
6. Выложить с заданным `LEADS_API_KEY`; после подтверждения приёма заявок вывести n8n-сценарий из эксплуатации отдельно.

Откат: вернуть предыдущую версию хука и форм — роут `/api/lead` при этом можно оставить, он неактивен без обращений клиента.
