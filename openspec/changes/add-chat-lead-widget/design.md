## Context

Полный план, сигнатуры и тексты лежат в `proposal.md`. Здесь собраны решения и отвергнутые альтернативы.

- Форма заявки встроена в одно место, `src/components/Cta.astro` (`CtaForm`). У `/contact` своя `ContactForm`.
- `/api/lead` принимает `name`, `phone`, `email`, `subject`, `message`, `source`, `payload`, `max`, `legalConsent`. Отдельного поля для резюме нет.
- Чат из `add-ai-chat-page` реализован. Сейчас историю присылает клиент, лимиты хранятся в памяти.
- Redis уже запущен: `ai-agency-chat-redis`, `127.0.0.1:6380`, с паролем. Адрес передаётся в `REDIS_URL`.

## Decisions

### Решение 1: inline-виджет в слоте формы

`ChatWidget` повторяет обёртку и заголовок `CtaForm`. Меняются две строки в `Cta.astro`.
Альтернатива — плавающая кнопка: она не заменяет форму на месте. Отклонено.

### Решение 2: черновик через метки в ответе модели

Модель ставит в ответ метки `<consent-request/>` и `<lead>{name,phone,email,summary}</lead>`, сервер их вырезает и проверяет.
Альтернатива — tool calling: в PolzaAI не проверен. Отклонено для первой версии.

### Решение 3: модель предлагает, человек подтверждает

`/api/chat` только сохраняет проверенный черновик в Redis. Заявку отправляет `/api/chat-lead`, когда посетитель нажимает кнопку в карточке, где резюме можно отредактировать.
Альтернатива — отправка сразу по метке модели. Отклонено: инъекция или ошибка модели привели бы к заявке без подтверждения.

### Решение 4: общая функция `submitLead`

Логика `/api/lead` переносится в `src/lib/server/leads/submit-lead.ts` без изменений. Оба роута вызывают её напрямую.
Альтернатива — HTTP-запрос сервера к собственному `/api/lead`. Отклонено.

### Решение 5: резюме в существующем `message`

Контракт `/api/lead` не меняется. Длину резюме и удаление HTML проверяет чат.
Альтернатива — новое поле `summary`. Отклонено: платформа его не знает.

### Решение 6: Redis — источник истины для контекста

Ключ `chat:ctx:<chatId>` хранит JSON `{ createdAt, messages ≤ 40, consentRequestedAt, consentAcceptedAt, consentVersion, leadDraft, leadSent }` с `EXAT createdAt + 24 ч` (абсолютный срок, см. решение 12; исходный скользящий TTL заменён). `chatId` — UUID v4 из `crypto.randomUUID()`, сервер проверяет формат. Клиент присылает только `chatId` и новое сообщение. Согласие ставит сервер по своему времени при `acceptConsent: true`. Черновик и `leadSent` хранятся только в Redis. `/api/chat-lead` берёт из тела запроса лишь отредактированное резюме.
Альтернатива — история и состояние на клиенте (как в `add-ai-chat-page`). Отклонено требованием пользователя: клиенту нельзя доверять согласие и статус заявки.

### Решение 7: клиент `redis@6.3.0`

Официальный node-redis, текущий `latest` (npm registry), `engines.node >= 20`. API проверен по context7 `/redis/node-redis`: `createClient({ url })`, `.on("error")`, `connect()`, `set(k, v, { EX, NX })`, `get`, `del`, `isReady`, `destroy()`, `disableOfflineQueue`, `socket.connectTimeout`, `socket.reconnectStrategy`, `commandOptions.timeout`.
Один модуль `src/lib/server/redis.ts` подключается лениво, команды не ставит в очередь, таймауты по 2 с. Ошибка превращается в `RedisUnavailableError`, роут отвечает 503, в лог раз в минуту пишется фиксированная строка без URL.
Альтернатива — `ioredis`. Отклонено: второй клиент без явных преимуществ, а node-redis — официальный.

### Решение 8: лимиты остаются в памяти

Лимиты `checkRateLimit` (20 за 10 минут, 300 в час) и новый `checkLeadLimit` (2 заявки в час с клиента, 30 в час на сайт) работают в памяти одного процесса, как в `add-ai-chat-page`. Пользователь просил хранить контекст, а не лимиты. Инстанс один.
В Redis переносится только маркер дубля телефона (`SET NX EX 1800` по SHA-256 цифр): он должен пережить рестарт и быть атомарным. Если отправка не удалась, маркер снимается.

### Решение 9: привязка контактов к сообщениям посетителя в Redis

Черновик принимается, только если имя, 10 цифр телефона и email есть в сообщениях посетителя из Redis. Клиент эту историю подменить не может.

### Решение 10: телефон обязателен

Как в форме и в `/api/lead`. Если посетитель не даёт телефон, агент отправляет его на `/contact`.

### Решение 11 (security review): согласие запрашивает сервер

Сервер ставит `consentRequestedAt`, когда возвращает `consentRequired`. `acceptConsent` принимается только в течение 30 минут после этого и не перезаписывает действующее согласие. В состоянии и в `payload` хранятся `CHAT_CONSENT_VERSION` и SHA-256 отпечатка текста. Если версия текста сменилась, старое согласие считается недействительным.

### Решение 12 (security review): абсолютный срок 24 часа

`createdAt` записывается при создании. `SET … EXAT createdAt + 24 ч` выполняется при каждой записи, поэтому срок не продлевается. Чтение TTL не меняет. Просроченное состояние читается как пустое и удаляется. После отправки заявки история и черновик стираются.
Альтернатива — скользящий TTL. Отклонено: срок хранения ПДн можно было бы продлевать бесконечно.

### Решение 13 (security review): ключ клиента по `clientAddress`

По умолчанию `X-Forwarded-For` игнорируется. `TRUSTED_PROXY_HOPS` (по умолчанию 0) явно задаёт число доверенных прокси. Значение выбирает человек при выкладке (Dokploy/Traefik обычно 1).

### Решение 14 (security review): блокировка на chatId

`SET chat:lock:<id> <token> PX 60000 NX` берётся до чтения состояния и снимается в `finally` через `EVAL` с проверкой токена. Если блокировка занята — 409. PX 60 с больше таймаута модели (30 с) плюс запаса на каталог и Redis.
Альтернативы: WATCH/MULTI неудобен при долгом вызове модели между чтением и записью; слияние состояний сложнее и хрупко. Отклонены.

### Решение 15 (security review): мелкие исправления

- L1: имя и email совпадают целым словом или токеном; автотекст согласия не участвует в проверке.
- L2: лимит заявок считается после захвата маркера; маркер остаётся при сетевой неопределённости.
- L3: ключ маркера — HMAC с `CHAT_LEAD_HASH_SECRET`.
- L4: логи отказов платформы без `details`.
- L5: `REDIS_URL` без пароля отклоняется.
- L6: `noeviction` рекомендуется как решение по выкладке.
- L7: логика состояния вынесена в `chat-state.ts` и проверяется unit-тестами с поддельным хранилищем; тесты роутов не делаются из-за `astro:env`.

## Risks / Trade-offs

- **`TRUSTED_PROXY_HOPS` настроен неверно.** `0` за прокси — все посетители делят один лимит. `1` без прокси — лимит по клиенту можно обойти. Это решение человека при выкладке.
- **409 при двойной отправке.** Посетитель видит «Предыдущее сообщение ещё обрабатывается». Клиент и так блокирует ввод на время загрузки.
- **После отправки заявки модель теряет контекст**, потому что история стирается. Остаётся флаг «заявка отправлена».

- **ПДн в Redis** (имя, телефон, email, текст задачи) хранятся до 24 часов. Защита: TTL, пароль только в окружении, Redis слушает 127.0.0.1, содержимое и URL не логируются, ключ дубля хранит хеш. Шифрования на диске нет. Если в Redis включено сохранение на диск (RDB/AOF), данные попадают туда; настройки контейнера в этом изменении не меняются.
- **`REDIS_URL` из контейнера.** `127.0.0.1:6380` внутри контейнера сайта указывает на сам контейнер сайта. Перед выкладкой адрес нужно проверить.
- **Redis недоступен — нет канала заявок на страницах с CTA.** Остаётся только ссылка на `/contact`. Решение сознательное.
- **ПДн уходят LLM-провайдеру**, юридические документы нужно дополнить.
- **Старые вкладки** после выкладки шлют запросы старого формата и получают 400, пока страницу не перезагрузят.
- **Гонки.** Два одновременных запроса с одним `chatId`: побеждает последняя запись. Клиент блокирует отправку на время загрузки.
- **`source: cta-block` исчезает** из новых заявок.
- **Модель может не поставить метку** — тогда статус `invalid`, ссылка на `/contact` остаётся.
